# 사용자 앱 구현과 백엔드 연동

## 화면 하나를 맡았을 때

예를 들어 **RP-02 이번 회차 갚기**를 맡으면, 먼저 [요구사항](requirements.md)에서 역할이 채무자인지 확인한다. 시작 화면은 약속 상세다. 서버가 준 회차·남은 금액·등록 계좌를 보여 주고, 사용자가 납부액을 확인한 뒤 거래 PIN을 입력한다. 요청을 보낸 뒤에는 처리 중임을 표시한다. 성공 응답과 갱신된 내역을 확인하면 채무자에게 영수증을, 채권자에게 수령액과 잔액을 보여 준다. 요청 결과가 불확실한 경우 두 번째 송금이 생기지 않도록 기존 거래 상태를 먼저 조회한다.

기능을 나눌 때는 화면에는 입력·표시·이동을, 공통 API 계층에는 Gateway 주소·인증·오류 처리를, 기능별 데이터 처리에는 계약·회차·버전과 서버 응답 변환을 둔다. 기존 구현을 통합하면 실제 디렉터리를 README에 연결한다. 두 명이 병행할 때 한 명은 사용자 행동을, 다른 한 명은 그 행동을 받은 상대방 화면을 검증하면 누락을 찾기 쉽다.

## 단계별로 검증할 경계

| 단계 | 화면이 확인할 것 | 동료가 재현할 예 |
| --- | --- | --- |
| 가입·계좌 | 테스트 본인인증 안내, 필수·선택 약관, 본인 명의 계좌 인증과 거래 PIN, 계정별 데이터 분리 | 로그아웃 뒤 뒤로 가기와 앱 복귀로 직전 사용자의 약속이 노출되는지 확인 |
| 연결 | 일회용 QR 또는 지정 수신자 초대, 양측 상대 확인 | 같은 QR 재사용·만료, 링크를 다른 계정으로 열기, 한쪽만 확인한 상태 |
| 협상 | 제안한 사람, 현재 응답할 사람, 조건·버전·이력 | 역제안 뒤에 이전 제안을 열어 둔 기기에서 수락 시 최신 조건 재조회 |
| 서명 | 양측이 같은 원문과 요약 열람, 안전 확인·본인 서명, 문서번호와 체결 시각 | 한 명만 서명하면 대기, 둘 다 서명하면 체결 증명, 이전 원문 재열람 |
| 대여·취소 | 체결 계좌·금액과 PIN, 미송금 시 합의 취소, 24시간 미송금 시 차주의 취소 자격 | 송금과 취소가 겹치면 서버가 확정한 한 가지 결과를 양쪽에 표시. 기한 기산 시각은 서버 계약에 명시 |
| 상환·정정 | 회차별 잔액, 외부 입금 매칭, 양측 영수증 | 같은 입금 재선택, 부분 납부와 조기 납부, 잘못 반영한 입금 정정 후 이력 |
| 조건 변경·종료 | 변경 전후 조건과 사유, 두 사람의 재서명, 완납 증명과 종료 계약 조회 | 한쪽만 재서명하면 기존 일정 유지, 양측 재서명 후 새 일정과 원래 문서를 각각 확인 |

## 실제 API로 바꿀 때

1. BE 담당자와 이슈에서 메서드·Gateway 경로·인증·요청 필드·응답 예시·실패 코드·재조회 방법을 확인한다. 거래는 중복 방지 키의 범위와 재사용 규칙, 계약은 문서 버전과 충돌 응답을 함께 확인한다. 합의한 문서 링크와 확인 날짜를 PR에 남긴다. [팀 API 문서](https://github.com/cnsFinalProject/Backend/tree/develop/docs/api)
2. 사용자 명령은 REST로 보내고, 서버가 확정한 금액·일정·상태를 표시한다. 실시간 연동 시 STOMP 알림을 받으면 권한 있는 계약과 관련 목록을 다시 조회한다. 재연결·포그라운드 복귀 때도 같은 규칙을 쓴다. 현재 계약·버전과 맞지 않는 늦은 응답으로 새 상태를 덮어쓰지 않는다.
3. 토큰 갱신을 공유해 여러 요청의 동시 만료를 처리한다. 로그아웃·계정 전환 때 개인 캐시와 구독을 정리하고 이전 세션의 응답을 버린다. 앱과 관리자 웹은 각 환경에서 합의한 세션 보관 방식을 적용한다.
4. 첫 조회, 0건, 처리 중, 접근 거부, 재시도 가능한 실패, 결과 확인 중을 구분한다. 거래 결과가 불명확하면 상태를 조회하고, 완료된 요청의 재전송으로 금액이 두 번 반영되지 않는지 확인한다. 버튼을 잠그는 것만으로 서버 측 검증을 완료 처리할 수 없다.
5. 실연동 PR에는 가상 계정 두 개의 사전 조건, 재현 순서, 양측 최종 상태, 명령·빌드 결과를 남긴다. 목업 검증만 했으면 남은 실제 API 검증을 명시한다.
